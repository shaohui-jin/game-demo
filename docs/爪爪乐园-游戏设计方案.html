v3.0 相对 v2.0 的核心变更

① 经济模型不再重构——沿用原版的产出 / 消耗平衡。付费商品本身就是经过市场验证的货币回收池，没有理由推翻重做。唯一改动是货币来源：真实支付 → 模拟充值。

② 体力系统回归原版——上限 100、每 2 分钟恢复 1 点、每日 12:00 / 18:00 / 24:00 三段补贴、四档钻石补充价全部照搬，仅在商城增加一个买体力的快捷入口。

③ 删除"拟联网包装层"——不做假排行榜、假世界频道、假好友。保留签到、每日限时商店等有实际玩法价值的功能。

④ 删除"开发者模式"——已被模拟充值取代，无需重复出口。

⑤ 新增"分享与分发"章节——目标从"自己玩"扩展为"自己玩 + 分享给朋友"，需配套存档导出、布局分享码、多形态打包方案，美术原创性风险等级相应上调。

⑥ 限购按类别差异化放开——礼包拆成两类：阶段性礼包保持限购（超值但限量），商城礼包不限购（常驻但定价更高，约 9 折）；金币类商品全部不限购；体力包维持原版每日重置的价格阶梯与次数，不做破解改造；收集品不限购，重复获得自动转换为金币或钻石。详见 10.4 节。

⑦ 确立破解架构原则——模拟充值做成独立旁路模块（只负责往钻石余额加钱），所有商品逻辑完全按原版实现、一行不改。这样将来去掉破解功能或切回商业版时零改造。

⑧ 确认产品形态——竖屏、手机为主，首发形态为网页版（分享给朋友 / 覆盖 iOS）+ 安卓 APK（自己玩）。详见 13.1 节。

⑨ 技术栈改为纯 HTML5（DOM + CSS + Canvas）——放弃 Cocos Creator。原因是 Cocos 需在 GUI 编辑器手工搭场景、无法代码化交付；而本作 80% 内容是 UI，DOM + CSS 效率高得多。Cocos 的粒子与骨骼动画能力分别由 Canvas 2D 叠加层与 Rive 覆盖。MVP 周期相应从 10 周缩短至 8 周，P0 原型已完成。

⑩ 玩法基线重新校正（2026-09-28）——此前对"发射器/母体"体系的理解有多处错误：发射器不是固定挂件而是合成链的一部分；链的终点是母体或纯任务物品；母体不可合并、耐久耗尽即消失（本质是"一次性物资包"）；一个发射器可产出 1~3 种物品且有掉落概率。完整拆解见独立文档 肥鹅健身房-玩法机制拆解.html。

⑪ 体力模型修正——由"每日 12:00 / 24:00 定点回满"改为每 2 分钟恢复 1 点 + 12:00 / 18:00 / 24:00 三段可领补贴。详见 11 节。

⑫ 次数继承规则定稿为「甲 · 重置为满」+ 新增礼包链（2026-09-28）——合成出的发射器耐久一律回满、不继承素材剩余次数。该规则在单级链里会退化成机械操作，因此必须配套跨等级的中段发射器才能成立：点剩最后 1 次 → 合成后回满 → 中间点掉的次数全部白赚，定位是给玩家的隐藏福利。为此在 P0 中新增「礼包链」（伴手礼 Lv1 → 豪华礼盒 Lv2，均可点击产货币），并明确链的终点只有两种：母体 或 纯任务物品，两者都不可再合成。详见 4.2 / 4.3 节与 肥鹅健身房-玩法机制拆解.html 第 10.4 节。

⑬ P0 原型完成度——发射器掉落表与概率、发射器出现在链中段、甲规则、资源型掉落（金币 / 钻石直接进余额不占格子）、体力系统、旧存档迁移均已落地；配套 3 套自动化测试（纯逻辑 / 冒烟 / 存档），可一键回归。

02主题包装：为什么猫狗比鹅更值得做

换皮是低级做法。猫狗主题的真正价值在于，它能在不改动核心玩法的前提下，天然解决原版三个结构性瓶颈。

瓶颈原版（鹅）猫狗版优势
可收集角色池太窄 鹅的形象单一，只能靠造型和配色区分，角色扩展天花板低 猫狗品种天然丰富——布偶、橘猫、暹罗、哈士奇、柯基、柴犬、金毛……角色池扩容 10 倍以上，且用户对品种有天然认知，不需教育成本
人设与剧情难写 鹅缺乏普遍认知的性格标签，故事线要靠文案硬造 品种自带性格预设（哈士奇拆家、柯基短腿欢脱、布偶高冷），人设可直接调用用户既有印象
缺乏玩法分支的天然理由 单一物种，很难做出合理的双线设计 猫与狗的习性差异，为"双阵营双棋盘"提供不需要解释的世界观基础

2.1 世界观与包装映射

玩家身份从"健身房店长"变为"爪爪乐园店长"——经营一家猫狗日托乐园，为毛孩子提供洗护、玩耍、训练、住宿、诊疗服务。

原版元素猫狗版对应包装增益
肥鹅顾客猫狗顾客（按品种区分）品种即角色，收集欲更强
健身房功能区乐园功能区（洗护区、玩耍区、训练场、餐厅、午睡区、泳池、诊疗室、摄影棚）功能区与服务内容对应关系更直觉
健身器材合成链宠物用品合成链（玩具、零食、洗护、家具、医疗）物品更萌、更具分享欲
肥鹅造型宠物造型（项圈、领结、小衣服、帽子）装扮是宠物内容的天然爆点
订单抽屉剧情毛孩子的故事（每只专属 3–5 段）情感浓度更高

03核心循环设计

主循环与对标产品保持一致，但把"装饰升级"和"区域解锁"做了明确的资源分离：星星只管装饰（审美消费），经验只管解锁（硬性进度），避免原版中两者边界模糊导致决策困惑。

玩家单次会话的完整动线

打开游戏 → 读取存档 → 领每日签到奖励 → 收离线期间常驻宠物的产出 → 清理棋盘（卖掉低价值产物）→ 点击发射器攒素材 → 二合到订单所需等级 → 交付 3–5 个订单 → 拿星星装饰 + 攒经验 + 攒金币 → 逛每日限时商城 → 体力耗尽 → 视情况去充值中心补体力 → 下线

关键设计原则

单次会话必须能在 3 分钟内完成一次完整闭环（合成→交付→拿奖励）。碎片化是这类产品的生命线。

4.2 发射器设计

⚠️ 本节已按实现结果修正（2026-10-02 第二轮）——两条原设计是错的

错误 ①「点一次冷却一次」。原实现把玩具架（4s）/ 玩具箱（10s）做成了"点一下就转圈"的按钮。正确模型是「储备 + 一次性冷却」：buffer 是储备上限（能连点几次），refillMs 是储备耗尽后的冷却时长。玩家应当能一口气把储备点完，再去干别的，而不是每次点击都等。

错误 ②「发射器是棋盘外面的一条工具栏」。玩具架 / 玩具箱现在是主场景里的常驻对象（占棋盘格），可以被拖进背包暂存，也可以两两合成升级（2 个玩具架 → 1 个玩具箱）。它们在数据上就是一条独立的设施链 fac，因此拖拽 / 背包 / 存档 / 渲染全部复用既有机制。

★ 核心机制：储备耗尽之后的三种命运

「母体点完不一定就没了」—— 这是对标产品的关键玩法，现已落地为三种显式行为，并全部写进图鉴：

类型规则本项目实例
冷却型refillMs > 0：储备耗尽后进冷却，到点自动补满，主体永不消失玩具架（储备 8 / 冷却 60s）、玩具箱（储备 12 / 冷却 90s）、美容台（储备 8 / 冷却 120s）
转化型refillMs = 0 + exhaust.convert：原地变成另一样东西，形成链与链之间的衔接猫城堡 → 伴手礼（接入礼包链）；豪华礼盒 → 玩具架（白拿一个常驻设施）
消失型refillMs = 0 且无 exhaust：一次性物资包，用完就没了铃铛球 / 洗澡球 / 鲜鱼排（都是链中段的 Lv3）

为什么这样分：冷却型负责"无尽产出"（稀缺的是体力与空间，不是基础物品）；转化型负责"链路衔接"（给玩家一个惊喜的下一步）；消失型只留给链中段，保住「甲·重置为满」那条取舍 —— 如果所有发射器都永不消失，合成链的决策深度会塌掉。

发射器按操作方式分四类，这是控制玩家节奏的核心杠杆——点击型给主动收益，自动型给被动收益，冷却型给"回来看看"的理由。四类在代码里都已有对应物；棋盘上的具体设施和数值见 docs/现状.md。下表是对标原版的发射器规划，不是当前棋盘上的对象清单。

隐藏机制：次数继承规则 —— 已定稿为「甲 · 重置为满」

原版社区对此流传两种互相矛盾的说法："点剩最后一次再合成"（暗示点掉的次数不白点）与"2 级点了会影响三级次数"（暗示有继承惩罚）。本项目裁定为「甲 · 重置为满」：合成出的发射器耐久一律回满，两个素材各自剩多少都不继承。定位是给玩家的隐藏福利。

★ 这条规则的价值完全取决于链的结构。它要求链上存在跨等级的中段发射器（两级都可点击、可合并，如原版手提包 Lv1 → Lv2）。此时玩家会发现："点剩最后 1 次 → 合成后回满 → 中间点掉的次数全部白赚"，"什么时候停手"于是变成有正收益的取舍（点掉 = 立刻换低价值产出；留着 = 延迟换高价值产出）。反之，如果发射器只出现在链的顶端（合到顶即母体、母体不可合并），甲就退化成"合前点到剩 1 次"的机械操作，福利无从体现。

配套要求：合成后必须立刻用飘字 / 提示把"你之前点掉的 N 次白赚了"显性化。这类"可被发现的隐藏收益"是社区内容的重要燃料，但前提是玩家真的能发现它——藏着不说等于没有。

链的结构：终点只有两种，但发射器可以在中段

终点只有两种：① 母体——可点击产出下一条链，储备耗尽后按 4.2 的三种行为收尾（冷却续命 / 原地转化 / 消失）；② 纯任务物品——只用于交付订单。两者都不可再合成。

但发射器也可以出现在链的中段：既能点击产出，又能继续往上合。这正是「甲 · 重置为满」得以成立的前提。设计时必须刻意在每条链上留至少一个中段发射器，否则整条链的决策深度会塌掉。

中段发射器实例（礼包链，已落地 P0）：

4.3 合成链设计（猫派 5 条 + 狗派 5 条 + 共用 4 条）

✔ 已实现：第三条链的深度与命名（2026-10-02 第三批「内容扩容」）

本节按 10 条合成链规划（猫派 5 + 狗派 5 + 共用 4）。目前实际落地的是 5 条：设施链（5 级，产出源头）、玩具链 / 护理链 / 食物链（各 7 个普通等级 + 1 个顶端 = Lv8）、礼包链（4 级，货币线）。名单与数值见 docs/现状.md。

命名取自本节下方各链的方案，只做了一处顺序适配：本节把母体（猫城堡 / 美容台）排在链的中间，而实现中母体必须是链的终点，所以它们被放到 Lv8。Lv1–3 与本节方案完全一致。

未实现的 5 条（训练链 / 医疗链 / 清洁链 / 货币链 / 舒适链）留待后续批次；设施链与礼包链是本节没有的新增内容。

07差异化创新：五个必须加的东西

如果只是换皮，产品没有辨识度。以下五点是在不改动核心循环的前提下，能形成差异的设计。

01 · 猫狗双阵营

猫派 / 狗派各一套独立合成链，产物不互通，共用棋盘。玩家可双线并行或专精一线，专精线解锁"猫之大师 / 狗之大师"称号与专属装饰。开局即需做一次身份选择，强化代入感。

02 · 顾客 → 常驻宠物

好感度满格的顾客转化为常驻宠物，每小时自动产出一次资源，离线最多累积 8 小时。这是纯新增的放置收益层，解决原版"上线才有收益"的弱点。

03 · 时段与天气系统

白天狗多、夜间猫多；雨天触发特殊事件（狗狗弄脏了 → 洗护订单翻倍）。让"什么时候玩"本身成为决策。

04 · 猫狗羁绊

特定猫 + 狗组合摆放在同一区域，触发互动动画并产出稀有物品。例如「布偶猫 + 金毛 = 相拥午睡」→ 产出稀有装饰"温暖毛毯"。为装饰系统赋予功能性。

05 · 宠物代打（放置深化）

常驻宠物可被派遣去"帮忙点击发射器"N 次。离线期间自动消耗耐久并产出素材，把放置收益从"资源"延伸到"操作"。这是把体力瓶颈转化为养成动力的关键设计。

08角色设计：首批 24 只

09经济结构：沿用原版 + 模拟充值

设计原则：不重构经济

原版的产出 / 消耗平衡是经过市场验证的——那些需要真实付费的商品，本身就是最合理的货币回收池。既然付费体系整体保留，就没有理由推翻经济模型重做。

10.4 破解版的限购与商品设计原则

取消限购不是简单地"把限制删掉"。正确的做法是把礼包拆成两类——超值的限量卖，不限量的卖贵一点，两者分工明确。

类别限购定价策略
阶段性礼包
新手、区域解锁、等级、节日礼包		 保持限购 超值（约单买的 5–7 折）。因为是限量的，超值不会造成套利
商城礼包

阶段性礼包 = 超值但限量，给玩家"抢到"的感觉；商城礼包 = 不限量但更贵，满足"想买就买"的即时需求。

这样设计的好处是两者互不冲突：玩家不会因为商城礼包存在而觉得阶段性礼包没价值（因为商城礼包更贵），也不会因为阶段性礼包限购而买不到东西（因为商城礼包随时能买）。

体力包：必须每日重置次数与价格

一个容易做错的地方

体力包的价格递增机制必须每天 0 点重置——价格回到 5 钻起，购买次数同步恢复。

如果做成"递增且不重置"，就会出现一个荒谬的情况：第一天买几次就涨到 40 钻，第二天还要从 40 钻开始。这意味着只要连续玩几天，体力就永远处在最贵档，体力补充彻底失去意义。

每日重置后的节奏是：每天前几次便宜（5 钻），越往后越贵（40 钻）。既保留了"多买有代价"的约束，又让每天的起步价可接受——与原版设计一致。

架构原则：破解功能做"旁路"，不做"改造"

这条原则决定了将来能否干净地切回正常版

模拟充值应该是一个独立模块，只做一件事：往钻石余额里加钱。所有商品的逻辑（体力包、礼包、会员卡、抽奖机）完全按原版实现，一行不改。

具体到体力这件事：破解版如果体力不够，玩家的做法是自己去模拟充值买钻石，而不是把体力包改成不限次数。这样体力包的代码永远不需要为破解做任何特殊处理。

好处有三：

① 将来去掉破解功能时零改造——只需隐藏模拟充值入口，商品系统、体力系统、数值平衡全部原样保留；

② 可以随时切回商业版——如果哪天想认真做一个正常版本，把模拟充值模块摘掉即可，不需要重写商城；

③ 分享给朋友时可自由选择——想让他们体验原版数值就关掉破解开关，想让他们随便玩就打开。

收集品重复获得的处理

收集品（限定造型、限定角色、限定装饰）不限购，可以重复获得。但重复获得时自动转换为金币或钻石，按稀有度决定转换量：

稀有度重复获得时转换
普通装饰2,000 金币
稀有装饰8,000 金币
限定造型150 钻石
限定角色300 钻石

这样抽奖机不会出现"抽到重复就白抽"的挫败感，收集品池也始终有实际价值。

单机版的体验优势：概率可以完全透明

原版因"抽奖概率不透明"被投诉。单机版不存在合规压力，反而可以把概率表直接做进游戏界面——点击"概率详情"就能看到每一项的精确百分比和累计抽取统计。这既消除了玩家疑虑，也是一个可以主动提及的体验优势。

④ 纯 Web 无构建流程，改一行刷新即见。对一个需要反复调手感、调数值的项目，这个效率差会累积成大量时间。

13.3 存档安全（单机版最重要的工程问题）

原版最大的用户投诉是"BUG 导致道具丢失"。单机版的等价风险是存档损坏或被浏览器清除，导致几十小时进度归零。考虑到还要分享给朋友，这一点更为关键——朋友的存档丢了，体验直接崩掉。

  • 自动存档：每次关键操作（合成、交付订单、购买）后异步写入，不阻塞主线程
  • 多槽位备份：保留最近 5 个自动存档快照，滚动覆盖，可回滚到任意快照
  • 手动导出 / 导入：一键导出存档为 JSON 文件下载到本地，可随时导入恢复
  • 存档版本号：每次版本更新做数据迁移，避免旧存档无法读取
  • 异常捕获：全局错误监听，崩溃前强制写一次存档
  • 首次启动提示：明确告知玩家"存档保存在本地浏览器，建议定期导出备份"

13.5 布局分享码：零服务器实现方案

先厘清一个容易踩的坑

"短码"和"分享码"是两回事。

短码（如 6 位的 PP-7K3M9）确实需要服务器——它的原理是"用短 ID 去后台查对应的长数据"，没有后端就查不到。这类方案直接排除。

自包含码不需要服务器——把布局数据全部编码进码本身，朋友解码即得，全程零网络请求。本项目采用这一方案。

数据打包流程（全部在客户端完成）

01
提取布局数据
遍历乐园中所有装饰物，取出物品 ID、坐标、朝向、外观变体
02
二进制位打包
每个装饰物压到约 3 字节：物品 ID 变长编码 + 坐标 + 朝向外观位域
03
压缩
用 LZ-string（纯 JS 库，无依赖，可完全离线运行）二次压缩
04
Base32 编码
剔除易混淆字符（0/O、1/I/L），避免手抄出错
05
加元数据
1 字节版本号（便于未来格式升级）+ 2 字节 CRC 校验（输错能立刻发现）

Base32 编码后约 288 字符
含元数据总长约 300–400 字符

这个长度复制粘贴完全可用，渲染成二维码也处于舒适区间（约 QR version 13–15，手机上显示与扫描均无压力）。

  • 无需任何后端成本——真正的零运维

13.6 跨设备数据同步方案

先明确三个前提

① 没有服务器——这是硬约束，任何同步方案都不能依赖自建后端。

② 存档体积不统一——布局分享码只有几百字节（二维码装得下），但完整存档是数百 KB 到数 MB（含图鉴、布局、宠物状态、活动进度），二维码完全装不下。这两者必须用不同的同步通道，不能混为一谈。

③ 存档是整体状态——不像文档能做字段级合并。这意味着同步的核心难点不是"怎么传"，而是"两边都改过时听谁的"。

四层方案（按依赖程度递增）

层级方案实现方式依赖推荐度
L1 手动导出 / 导入 存档导出为文件或文本码，通过微信"文件传输助手"自己中转，另一台设备导入 无 ★★★★★ 必做基线
L2 网盘目录同步（仅桌面端） 桌面版存档路径可配置，指向 OneDrive / 坚果云同步目录，网盘自动同步文件 用户自己的网盘 ★★★★ 偷懒方案
L3 WebDAV 自动同步 用户填入自己的坚果云 WebDAV 地址与账号，游戏自动上传 / 下载存档 用户自己的 WebDAV 账号 ★★★★★ 自动同步最优解
L4 HTTP 适配器（架构预留） 定义好接口，未来若有服务器可直接接入，无需改动上层逻辑 未来的服务器 架构预留

L1 · 手动同步（必做基线）

这是零依赖的保底方案，必须在 MVP 阶段就做好。三种中转方式，都利用用户已有的工具：

  • 微信文件传输助手——最实用。手机上导出存档文件发给自己，电脑上从文件传输助手下载后导入。用户本来就有微信，不需要任何额外配置。
  • 文本码复制粘贴——适合小数据（布局）。完整存档太长，不适合。
  • 二维码——仅适用于布局分享（几百字节）。完整存档二维码装不下，不要尝试。

L2 · 网盘目录同步（桌面端偷懒方案）

零代码实现跨设备同步

桌面版的存档是本地文件。只要把存档路径做成可配置项，用户把它指向 OneDrive / 坚果云 / Dropbox 的同步目录，网盘客户端就会自动把存档同步到其他设备——游戏代码一行同步逻辑都不用写。

局限：仅桌面端可用；网盘同步有延迟（通常几十秒到几分钟）；多设备同时改仍有冲突风险。

L3 · WebDAV 自动同步（推荐，零服务器自动同步）

这是"没有自己服务器"前提下能做到的最优自动同步方案。原理是让用户提供自己的存储空间，游戏只负责读写：

01
用户配置
在设置页填入 WebDAV 地址、账号、应用密码（坚果云可免费申请）
02
连接测试
游戏发起一次读写测试，确认凭据有效并显示连接状态
03
自动上传
关键操作后延迟数秒自动上传存档，带时间戳与设备 ID
04
启动检查
游戏启动时比对云端与本地的存档时间戳，提示是否需要拉取

优点：数据在用户自己手里、零成本、跨平台（手机浏览器与电脑浏览器都能连）、一次配置长期有效。
缺点：配置有门槛，需要引导文档（教用户申请坚果云应用密码）。

L4 · 架构预留：SyncAdapter 接口

这是本方案最重要的一条架构建议——不要把同步逻辑写死。定义一个抽象接口，把"传输"和"玩法"彻底解耦：

interface SyncAdapter {
  name: string                            // 适配器名称
  isConfigured(): boolean         // 是否已配置完成
  upload(save): Promise<void>     // 上传存档
  download(): Promise<Save>      // 下载存档
  getRemoteMeta(): Promise<Meta> // 取云端元数据（时间戳/版本/设备）
  detectConflict(local, remote): Conflict | null
}

上层玩法代码只依赖这个接口。换同步方式不需要改任何玩法逻辑——今天用手动导出，明天想加 WebDAV，后天有了服务器想接 HTTP，都只是新增一个实现类。

冲突处理（同步的真正难点）

存档是整体状态，无法做字段级合并。因此策略应该是"明确比较 + 冲突时让用户决定"，绝不做静默覆盖：

场景判定处理
云端比本地新云端时间戳 > 本地，且本地未被修改过自动拉取云端，提示"已同步最新进度"
本地比云端新本地时间戳 > 云端，且云端未被其他设备改过自动上传本地
两边都改过（分叉）本地与云端的 baseVersion 相同，但各自时间戳都更新了不自动覆盖。弹出对比界面，显示两边的等级、金币、游玩时长、最后修改时间，让用户选择保留哪一份
首次同步云端为空直接上传本地作为基线

每份存档需携带三个字段用于冲突判定：lastModified（时间戳）、deviceId（设备标识）、baseVersion（上次同步的版本号）。

一个现实提醒

iOS Safari 对 IndexedDB 有清理策略——长期不访问的站点数据可能被系统回收。因此"定期导出备份"的提示不能省，尤其是 Web 版。如果用户主要在手机上玩，建议引导使用 L3（WebDAV）或干脆用安卓 APK / 桌面端，把存档落到本地文件更稳妥。

层级决策理由

L1 实施细节（以手机端为主场景）

一个必须先算清楚的账

完整存档压缩后约 100–200 KB。若编码成文本码，就是十几万到几十万字符——复制粘贴完全不现实，二维码更装不下。

所以结论是：L1 的核心是"文件导出 / 导入"，文本码与二维码只用于布局分享这类小数据。这两条通道不能混为一谈。

手机 → 电脑 的实际流程

  1. 手机游戏内点「导出存档」→ 浏览器下载一个 .paw 文件
  2. 在微信里把该文件发给「文件传输助手」
  3. 电脑微信里下载该文件
  4. 电脑游戏内点「导入存档」→ 选中该文件

电脑 → 手机 的实际流程

  1. 电脑游戏内点「导出存档」→ 得到 .paw 文件
  2. 微信发给「文件传输助手」
  3. 手机微信里打开该文件 → 保存到「文件」App
  4. 手机游戏内点「导入存档」→ 从系统文件选择器选中该文件

关键实现要点

  • 导出：用 Blob + a[download]。文件名必须带时间戳与等级（如 爪爪乐园_Lv23_20260928.paw），方便用户区分多个备份文件
  • 导入：用 <input type="file">，移动端会自动唤起系统文件选择器，无需额外权限
  • 导入前必须显示存档摘要——等级、金币、游玩时长、最后修改时间，让用户确认后再覆盖，避免误操作导致进度被旧档冲掉
  • iOS 适配：Safari 下载的文件会落到「文件」App，需在引导文案里明确说明路径，否则用户找不到
  • 一键复制分享码：布局分享码（小数据）提供"复制到剪贴板"按钮，微信里直接粘贴即可

为未来接服务端预留的数据契约

"预留"的关键不是留接口，是留数据格式

只定义 SyncAdapter 接口是不够的——如果存档格式现在是随手设计的，未来接服务端一样要重构。

因此本次实现 L1 时，就必须把存档设计成"未来能直接上传"的形态：统一的存档信封 + 纯 JSON 载荷。只要现在按这个格式落盘，未来接 WebDAV 或 HTTP 零重构。

统一存档信封（SaveEnvelope）

{
  "schemaVersion": 1,         // 存档格式版本，用于未来迁移
  "deviceId": "dev-a1b2c3",   // 设备标识，冲突判定用
  "lastModified": 1759048392, // 最后修改时间（Unix 秒）
  "baseVersion": 17,        // 上次同步的版本号
  "checksum": "9f3a...",     // 内容校验，防止文件损坏
  "payload": { ... }        // 实际游戏数据
}

这个信封是未来所有同步方式的通用载体：

  • L1 导出的 .paw 文件 = 这个 JSON（压缩后）
  • L3 WebDAV 上传 = 同一个 JSON
  • L4 HTTP 上传 = 同一个 JSON

三条必须从第一天就遵守的约束：

  1. payload 必须是纯 JSON——不含函数、不含平台相关对象（DOM 节点、Blob 引用、类实例）。否则无法序列化上传
  2. 所有时间统一用 Unix 时间戳（秒），不要用本地时间字符串（跨时区会出问题）
  3. schemaVersion 从第一天就带上，哪怕现在恒等于 1。没有版本号的数据格式，未来一定无法平滑迁移
未来接入服务端时的工作量

如果以上契约现在落实到位，未来接服务端只需三步：① 实现一个 HttpSyncAdapter；② 在设置页加一个"登录账号"入口；③ 在适配器列表里注册它。玩法代码、存档格式、冲突处理逻辑全部复用，零改动。
