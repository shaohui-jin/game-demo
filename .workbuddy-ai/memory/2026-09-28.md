## 《爪爪乐园》游戏设计方案（v1.0）

**任务**：用户希望基于《肥鹅健身房》的玩法，设计一款猫狗主题的同类游戏，输出方案。

**产出**：`D:\_myproject\game\爪爪乐园-游戏设计方案.html`（14 章完整设计文档）

**关键研究结论（《肥鹅健身房》对标基准）**
- 厂商：疯狂游戏（豪腾创想）；2020.09 版号，2021.11 重做加入合成玩法，开发周期<3 个月
- 核心：「合成 + 模拟经营」双循环。棋盘二合 → 交付顾客订单 → 星星/金币/经验 → 装饰升级 + 区域解锁 → 反哺新订单需求
- 8 个区域、13 个子系统；女性用户 >70%，24–30 岁为主
- 2025 上半年收入约 2171 万元；iOS 日均营收约 3.5 万美元
- 关键数值：订单基础奖励 15 经验/30 金币/40 好感；体力每日 12:00、24:00 刷新；商城 6/12/18/24 点刷新；广告 6 次/日=30 钻；棋盘扩容约 1000 金币/格
- 隐藏技巧：小肥鹅点 14 下合成中肥鹅，中肥鹅不点击直接合成大肥鹅，耐久不减（社区核心传播点）
- 投诉风险点：抽奖概率不透明、BUG 导致道具丢失、人机账号干扰排名、未成年充值

**方案核心设计决策**
- 命名《爪爪乐园》，场景为宠物日托乐园替代健身房
- 猫狗主题三大优势：角色池扩 10 倍、品种自带性格标签、双阵营有天然世界观依据
- 差异化五点：①猫狗双阵营双合成链 ②顾客→常驻宠物（离线被动收益）③时段/天气系统 ④猫狗羁绊组合 ⑤宠物代打（放置深化）
- 合成链：猫派 5 条 + 狗派 5 条 + 共用 4 条，Lv1–Lv8（部分 Lv9）
- 棋盘 7×9=63 格，初始解锁 35 格
- 技术选型：Cocos Creator 3.8 + NestJS/MySQL/Redis，微信小游戏首发

**下一步建议**：P0 原型验证手感 → 数值仿真 → 美术风格测试 → 确认首发市场（国内版号周期长则按出海立项）

## 补充修正：布局分享码的零服务器实现（用户指出问题）

**用户提问**：分享码岂不是需要后台服务？目前没有服务器。

**确认问题成立**：v3.0 初稿中写的 6 位短码 `PP-7K3M9` 确实需要服务器（短码原理 = 用短 ID 去后台查长数据）。已修正。

**修正方案（已写入文档 13.4 节）**
- 区分「短码」与「自包含码」：短码需服务器 → 排除；**自包含码把数据全部编码进码本身 → 零网络请求**
- 打包流程（全客户端）：提取布局数据 → 二进制位打包（每装饰物约 3 字节）→ LZ-string 压缩（纯 JS、可离线）→ Base32 编码（剔除 0/O/1/I/L 易混字符）→ 加 1 字节版本号 + 2 字节 CRC 校验
- 码长估算：60 个装饰物 ≈ 180 字节 → Base32 ≈ 288 字符 → 含元数据约 300–400 字符。复制粘贴可用，二维码约 version 13–15 舒适区间
- 三种零服务器分享方式：①分享图片（图片上同时印二维码 + 文本码，推荐★★★★★）②纯文本码 ③导出 .paw 文件（JSON）拖入导入
- **推荐三合一**：一张图同时提供二维码与文本码，覆盖全部场景
- 额外好处：永不过期、可离线传递、可塞彩蛋（自定义祝福语/署名）、零后端成本

**结论**：整个方案（含分享功能）确认可在无服务器条件下完整实现。**注意：本项目的"零服务器"是硬约束，后续任何涉及分享/排行榜/云存档的设计都必须先确认不需要后端。**

## 补充设计：跨设备数据同步方案（已写入文档 13.5 节）

**用户提问**：没服务器，手机上玩的数据怎么同步到电脑？是不是需要一个数据同步的口子？

**三个前提（必须先厘清）**
1. 没有服务器（硬约束）
2. **存档体积不统一**：布局分享码仅几百字节（二维码可承载）；完整存档数百 KB～数 MB（**二维码完全装不下**）。两者必须用不同通道
3. **存档是整体状态**，无法字段级合并 → 同步的真正难点是"两边都改过时听谁的"

**四层方案**
- **L1 手动导出/导入（必做基线，MVP）**：微信"文件传输助手"中转最实用；文本码适合小数据；二维码仅限布局分享
- **L2 网盘目录同步（仅桌面端，偷懒方案）**：存档路径可配置 → 指向 OneDrive/坚果云同步目录 → **网盘自动同步，游戏代码零同步逻辑**
- **L3 WebDAV 自动同步（推荐）**：用户填自己的坚果云 WebDAV 账号，游戏自动上传/下载。数据自主、零成本、跨平台。缺点：配置有门槛，需引导文档
- **L4 架构预留**：**SyncAdapter 抽象接口**（name / isConfigured / upload / download / getRemoteMeta / detectConflict）。上层玩法只依赖接口，换同步方式不改玩法逻辑

**冲突处理策略**：存档携带 lastModified + deviceId + baseVersion 三字段；云端新→自动拉取，本地新→自动上传，**两边都改过（分叉）→ 绝不静默覆盖，弹对比界面让用户选**

**现实提醒**：iOS Safari 会回收长期不访问站点的 IndexedDB 数据 → "定期导出备份"提示不能省；手机党建议用 WebDAV 或 APK/桌面端

**推荐落地组合**：MVP 只做 L1 → 第二阶段加 L3 + L4 → 长期若有服务器直接新增 HTTP 适配器，上层零改动

## 同步方案最终决策（用户已拍板，2026-09-28）

**用户决策**：先做 L1 手动导入导出；预留 L3/L4 以便未来接服务端。理由——主要在手机端游玩，跨设备同步是低频需求。

**决策表**
| 层级 | 决策 |
|---|---|
| L1 手动导出/导入 | **本次实现** |
| L2 网盘目录同步 | 不做（仅桌面端，与手机为主的场景不符） |
| L3 WebDAV | **只预留接口，不实现** |
| L4 HTTP 适配器 | **只预留接口，不实现** |

**L1 关键发现（重要）**：完整存档压缩后约 100–200KB → 文本码十几万到几十万字符，**复制粘贴不现实、二维码装不下**。因此 **L1 核心是"文件导出/导入"（.paw 文件），文本码与二维码只用于布局分享这类小数据**。两条通道必须分开。

**手机端流程**：手机→电脑：游戏导出 .paw → 微信文件传输助手 → 电脑下载 → 游戏导入。电脑→手机同理反向。实现要点：Blob + a[download] 导出，文件名带时间戳与等级（如 `爪爪乐园_Lv23_20260928.paw`）；`<input type="file">` 导入；**导入前必须显示存档摘要让用户确认**（防误覆盖）；iOS Safari 下载落到「文件」App 需在引导文案说明。

**为未来接服务端预留的数据契约（关键，光留接口不够）**
统一存档信封 SaveEnvelope：
```
{ schemaVersion: 1, deviceId, lastModified(Unix秒), baseVersion, checksum, payload }
```
- L1 导出文件 = 此 JSON（压缩后）；L3 WebDAV 上传 = 同一 JSON；L4 HTTP 上传 = 同一 JSON
- 三条硬约束：① payload 必须纯 JSON（不含函数/DOM/类实例）② 时间统一 Unix 秒 ③ schemaVersion 第一天就带上
- 未来接服务端只需三步：实现 HttpSyncAdapter → 加登录入口 → 注册适配器，**玩法代码/存档格式/冲突逻辑零改动**

**排期更新**：L1 + SyncAdapter 接口 + SaveEnvelope 数据契约 已并入 P1 阶段（第 4–7 周）

## 限购与商品设计原则（用户三次澄清后的最终版）

**已写入文档 10.4 节「破解版的限购与商品设计原则」+ 更新 9.2 / 10.3 表格 + 11 节体力说明 + 顶部变更记录 ⑥⑦**

**最终处理（关键：礼包拆成两类，不能一刀切）**
| 类别 | 限购 | 定价 |
|---|---|---|
| **阶段性礼包**（新手/区域解锁/等级/节日） | **保持限购** | 超值，约单买 5–7 折 |
| **商城礼包**（日常/进阶/豪华补给包） | **不限购** | 约单买 9 折，明显不如阶段性礼包划算 |
| 金币类商品（材料箱、沙漏、剪刀、扩容） | 不限购 | 维持原价 |
| **体力包** | **每日重置次数与价格** | 回归原版 5/10/20/40 阶梯 |
| 收集品（限定造型/角色/装饰） | 不限购 | **重复获得自动转换为金币或钻石** |

**两类礼包的分工逻辑**：阶段性礼包=超值但限量（给"抢到"的感觉）；商城礼包=不限量但更贵（满足"想买就买"）。两者互不冲突——不会因为商城礼包存在而觉得阶段性礼包没价值，也不会因为限购而买不到东西。

**体力包必须每日重置（用户纠正的关键点）**：价格递增若不重置，会导致"第一天买几次就涨到 40 钻，第二天还从 40 钻开始"——连续玩几天后体力永远在最贵档，体力补充失去意义。每日重置后节奏为"每天前几次便宜、越往后越贵"，与原版一致。

**★ 架构原则：破解功能做"旁路"，不做"改造"（用户提出，很重要）**
- 模拟充值 = **独立模块，只做一件事：往钻石余额加钱**
- 所有商品逻辑（体力包、礼包、会员卡、抽奖机）**完全按原版实现，一行不改**
- 体力不够 → 玩家自己去模拟充值买钻石，**而不是把体力包改成不限次**
- 三大好处：① 将来去掉破解功能**零改造**（只隐藏入口）② 可随时切回商业版 ③ 分享给朋友时可自由开关破解
- **这条原则应作为整个项目的代码组织准则，后续任何"破解特供"功能都必须是旁路注入，不得侵入原版逻辑**

**收集品重复获得转换表**：普通装饰 2000 金币 / 稀有装饰 8000 金币 / 限定造型 150 钻 / 限定角色 300 钻

**会员卡与成长基金**：会员卡不限购可叠加续期；成长基金不限购，重复购买重置返还进度。

```js
function pickRandomEmpty() {
  var empties = [];
  for (var i = 0; i < TOTAL; i++) {
    if (!isLocked(i) && state.board[i] === null) empties.push(i);
  }
  if (!empties.length) return -1;
  return empties[Math.floor(Math.random() * empties.length)];
}

// 2) 抛物线飞行：水平线性 + 垂直正弦弧线 + 随机旋转/缩放
function flyTo(fromEl, toIdx, lv, done) {
  var dur = 300 + Math.random() * 110;                 // 300–410ms 随机时长
  var arc = 46 + Math.random() * 52;                   // 46–98px 随机弧高
  var spin = (Math.random() > 0.5 ? 1 : -1) * (140 + Math.random() * 140);
  function frame(now) {
    var t = (now - t0) / dur;
    var x = sx + (tx - sx) * t;                                  // 水平：线性
    var y = sy + (ty - sy) * t - Math.sin(Math.PI * t) * arc;    // 垂直：抛物线
    var rot = spin * t;
    var sc = 1 + Math.sin(Math.PI * t) * 0.16;                   // 中段放大 16%
    el.style.transform = 'translate(' + (x - size/2) + 'px,' + (y - size/2) + 'px) rotate(' + rot + 'deg) scale(' + sc + ')';
    ...
  }
}
```

**★ 随机化设计要点**：时长、弧高、旋转方向与角度**三者均随机**，避免连续产出时出现节奏一致的机械感——这是原版"手感"的关键来源，不是单纯的随机落点。

## 震动二次修正：普通合成一律不震（用户反馈"合三级振幅大"）

**用户反馈**："合2级的时候效果还好，没有很大振幅，但是合三级的时候就会，不知道为什么"

**根因定位（不是 bug，是我设的阈值太低）**：上一版分级逻辑为
```js
var SHAKE = { merge: 0, high: 1.2, milestone: 2.4 };
var MERGE_HIGH_LV = 3;   // 合成结果达到 3 级就开始震
```
- Lv1+Lv1 → Lv2：`nextLv=2 < 3` → 走 merge 档，振幅 0 → 不震（用户说"效果还好"✔）
- Lv2+Lv2 → Lv3：`nextLv=3 >= 3` → 走 high 档，震 1.2px（用户说"振幅大"✘）

**关键认知（重要设计原则）**：**1.2px 看似很小，但震的是整个 `#app`（含 HUD + 棋盘 + 底栏），眼睛会跟整帧走，所以整屏位移的感知强度远高于同振幅的局部元素动画。** 结论：**屏幕震动不能按像素大小来判断是否"克制"，只能按"发生频率"来判断**。用在每次合成上必然是噪音，无论振幅多小。

**修正方案**：把阈值式的分级改成**语义化策略**——普通合成永不震，震动只留给稀有事件。
```js
var SHAKE = {
  milestone: 1.6,   // 合成出母体 / 顶级物品 / 等级提升
  byLv: {}          // 需要给某等级单独加反馈时填 { 5: 1.2 }，默认空
};
// 决策：
var amp = isMilestone ? SHAKE.milestone : (SHAKE.byLv[nextLv] || 0);
if (amp > 0) shake(amp);
haptic(isMilestone ? 26 : 11);
```
- 删除 `SHAKE.merge` / `SHAKE.high` / `MERGE_HIGH_LV` 三个阈值式常量
- `milestone` 振幅 2.4px → **1.6px**（同时覆盖"用户可能指的是用两个 3 级合出母体那一下"）
- 保留按等级自定义的入口 `SHAKE.byLv`，未来想给某等级加反馈直接填表

**补偿设计（撤掉震动后如何保留"越合越爽"）**：改用**局部粒子递增**承担等级反馈
```js
var lvBoost = Math.min(nextLv, 6) * 2;
burst(c.x, c.y, col, (isMilestone ? 30 : 18) + lvBoost, isMilestone ? 1.5 : 1.05 + nextLv*0.03);
ring(c.x, c.y, col, isMilestone ? 68 : 42 + nextLv * 3, isMilestone ? 4 : 3);
```
→ Lv2 约 22 粒 / 环 48px，Lv3 约 24 粒 / 环 51px，母体 38 粒 / 环 68px。反馈随等级平滑上升，但没有任何整屏位移。

**验证**：JS 语法 OK、div 30/30、文件 43,493 字节、无残留旧常量引用（SHAKE.merge / SHAKE.high / MERGE_HIGH_LV 均已清除）

### ★ 核心修正 1：术语是"发射器"，分两类，行为完全不同
| 类型 | 行为 | 来源 |
|---|---|---|
| **主要发射器** | 只有 CD，**不会消失、不会降级**。攻略原文："除了等 cd 没有任何后顾之忧" | 开局自带 |

→ **母体是一次性物资包，不是永久工具**。核心循环是"不断重新发育母体"。

### ★ 核心修正 2：发射器的三个属性
1. **产出表**：一个发射器产出 **1~3 种**物品，且有**掉落概率**（社区专门统计"爆率"）
2. **点击次数**（耐久）：点满即消耗掉自己

### ★ 核心修正 3：母体不可合并的准确含义（这条解开了我一直读不懂的技巧）
**维修工具箱链实例（攻略原文）**：
```
2 个工具箱把手 → 1 个箱盖
2 个箱盖 → 1 个空箱子
2 个空箱子 → 1 个简单五金盒
"简单五金盒可以开始生产工具啦，但是只能生产起钉器和单只手套噢"
```

**关键推论**：发射器可以出现在**链的中段**（手提包 Lv1/Lv2 都可点击、可合并升级），但**链的顶点是终点、不可再合并**。所以用户说的"母体不能合并"完全成立 —— 母体就是那个顶点。

这也解释了社区技巧"1 级不要点，合成 2 级再点"（次数成长非线性）。

## 【补充】次数继承规则定稿 + 礼包链落地（P0 原型 56,416 字节）

### 用户裁定：甲 · 重置为满
原话："甲吧，算是给用户的一个隐藏福利机制了"

**我推翻了自己对甲的评价**：此前判断"甲让最优解固定为合前点到剩 1 次、机械无决策"。
但这个判断漏了一点 —— **甲要有意义，前提是存在「跨等级的发射器链」**（原版手提包 Lv1/Lv2 都可点击）。
在跨级发射器链里，甲把规则升级成：**"点剩最后 1 次 → 合成后回满 → 中间点掉的次数全部白赚"**。
这不是"无决策"，而是把"什么时候停手"变成一个**有正收益的取舍**：点得越多赚得越多，
但点掉的是低等级产出（低价值），留着合成拿的是高等级产出（高价值）。
结论：**甲在单级链里是坏规则，在跨级链里是好规则。** 关键不是甲本身，而是链上必须有中段发射器。

### ★ 用 jsdom 搭了真实浏览器测试，抓出 4 个真实 bug（重要经验）
**教训：静态语法检查 + 纯逻辑仿真查不出 DOM 层与时序问题。必须真实加载页面跑一遍。**

1. **`renderTree` 用了 `top.produces`（启动即崩）** —— `ch.top` 是**原始链定义**（只有 `drops`），`produces` 只存在于 `defOf()` 的返回值上。`CHAINS[undefined].name` → TypeError。
   **规则：区分"原始链定义"与"defOf 返回值"，两者字段不同，不要混用。**
2. **资源掉落不刷新耐久徽标** —— 产货币走的是不经过 `emit()` 的分支，而 `renderBoard()` 只在 `emit()` 里调用 → 点一次货币，耐久数字停在旧值。
   **规则：任何改动 state 的分支都必须自己负责重建 DOM，不能依赖别的分支顺手调用。**
3. **孤儿物品会静默清空整份存档（最严重）** —— `defOf('ghost', 9)` 里 `CHAINS[k].items` 抛 TypeError，被 `load()` 的外层 `try/catch` 吞掉 → **load 返回 null → 整份存档被丢弃、退回全新开局**。讽刺的是，这个迁移循环本来就是为处理孤儿物品写的。
   **修复**：`defOf()` / `maxLv()` 对未知链返回 null / 0；迁移循环每项单独 try/catch。
   **规则：宽泛的 try/catch 是存档杀手。它会把"一个坏物品"放大成"数据全丢"。**
4. **重置存档后棋盘是空的** —— `freshState()` 不含种子，种子只在启动的 `if (!state)` 分支里加 → 重置出来与全新开局不一致。
   **修复**：抽出 `seedBoard()`，启动与重置共用。
5. **迁移结果没立刻回写** —— 加 `s.__dirty` 标记，启动时消费后删除并 `save()`。
